## Touch ID research (2026-10-14)

- **No public Linux Touch ID code exists for M1.** Searched GitHub (repositories and the omarchy-mac, omarchy-mac-pkgs and related repos), Asahi's docs and the Linux tree.
- Omarchy's September announcement says a developer "got Touch ID working by talking directly to the Secure Enclave" and lists it as a first-release target, but links no code. Omarchy's own package status page (`mac-manual/content/14-status.md`, omarchy-mac-pkgs 222f7a8) lists Touch ID under **"Not in the first release"**. These two statements disagree; the more specific, newer technical document says no.
- Asahi's [SEP page](https://asahilinux.org/docs/hw/soc/sep/) is research notes only: the Secure Enclave runs Apple's own firmware, which Linux cannot replace, so a driver must speak its mailbox protocol; the biometric endpoint (SBIO) is mapped but not verified; nothing is implemented. Asahi's M1 feature matrix says TouchID is TBA for every M1 variant.
- **What was added:** `mseries/local-ai/touchid-watch.py` plus a verify check `upstream-touchid-watch`. It watches the three places above (Omarchy status page, Asahi matrix, fairydust commits mentioning the Secure Enclave or Touch ID) and turns the check green when any changes. Today it reports no new signs.
- **Interim options (not installed):** a hardware security key with `pam_u2f` (touch the key instead of typing the password) works on Linux today and could cover login, lock screen and sudo; a short-lived trusted-device unlock is not available. Neither is Touch ID.
- **If a driver appears:** test in this order: the Secure Enclave device exists, enrolment works, PAM unlock for login, lock screen and sudo, with the password always kept as a fallback.

## iMessage evaluation (2026-10-14)

- **What OpenBubbles is:** an Apache-2.0 Flutter app plus the `rustpush` Rust library, which re-implements Apple's iMessage protocols. It "talks directly to Apple" with no server in between and impersonates a Mac, so it needs that Mac's hardware identifiers (serial number, board ID, model), obtained once from a real Mac through a helper app or in-app settings. After activation the Mac can be switched off. One Mac can serve up to 20 users.
- **Linux on this Mac:** the only published Linux build (v1.15.0+205, 2026-01-04) is `x86_64`. The source has a Linux target, a Flatpak definition and a build script that already handles `aarch64`, so an arm64 build is plausible, but it has not been attempted. Upstream's default branch (`rustpush`) builds against a sibling checkout of `OpenBubbles/rustpush` and needs the Flutter SDK (3.24 or newer) plus development packages that are not installed here (libsecret, ayatana-appindicator, webkit2gtk, jsoncpp). The older local clone in `~/Documents/openbubbles-app` (detached at the January commit) points `rustpush` at the author's home directory, so it cannot build as is. Rust 1.93 and clang, cmake and ninja are present.
- **Licensing (matters for the image):** `rustpush` is under the **Server Side Public License**, with special exceptions granted to OpenBubbles only. We can build and run it for ourselves, but we must **not bundle or redistribute it in the ElementaryOS image or this repository**. Keep it a personal, user-run install, and record the source revision. The app repository itself is Apache-2.0.
- **Apple account risk (from OpenBubbles' own FAQ):** accounts or devices are rarely blocked for a day or two, and in rare cases permanently (a call to Apple support usually lifts it); reusing someone's hardware identifiers for spam gets that Mac blocked; running it in a virtual machine is strongly discouraged; **Advanced Data Protection and Contact Key Verification must be turned off** for messaging to work; messages sent from it may not show on your other Apple devices for up to 24 hours; contacts may show as green (non-iMessage) for days if Apple throttles you. A phone number needs an always-online iPhone running their relay app.
- **Decisions only the owner can make** (an AI assistant must not enter Apple credentials): (1) accept the account risk above, (2) turn off Advanced Data Protection and Contact Key Verification on the Apple ID, (3) pick which Mac supplies the hardware identifiers (a different Mac than this M1 Pro is safer, since this one would then appear twice; `techmore-2` was online on the tailnet), and (4) type the Apple ID password and 2FA code into the app yourself.
- **Plan, after the reinstall:** install the build dependencies and Flutter, clone `OpenBubbles/openbubbles-app` (branch `rustpush`) next to `OpenBubbles/rustpush`, run `linux/build.sh`, launch the result, then do the activation steps above. Test send, receive, attachments and notifications. Signal stays the fallback.
- **Not done:** no build, no install, no sign-in.

## iCloud passwords evaluation (2026-10-14)

Apple publishes no Linux client for iCloud Keychain or the Passwords app. Its own browser extension exists for Windows only. Every Linux option below is an unofficial reverse-engineered project that signs in to your Apple ID, all are new (weeks to months old) and **declare no license** (fine for personal use, not for shipping in our image). Metadata checked on GitHub 2026-10-14; none was installed or run.

| Option | Direction | Notes |
| --- | --- | --- |
| [cameroncooper/keychain](https://github.com/cameroncooper/keychain) | Read only | Rust CLI written for Linux on Apple silicon: sync, search, passwords, TOTP codes, synced passkeys, optional Chromium extension. Validated by its author against a live account (including Advanced Data Protection). Its `join` step changes your Apple trust settings and escrow recovery has a server-enforced attempt limit, so read the warning first. Needs an anisette helper you supply. |
| [Sank6/iCloud-Keychain-for-Linux](https://github.com/Sank6/iCloud-Keychain-for-Linux) ("icp", 59 stars) | Read only | Python CLI and browser extension; passwords, TOTP, Hide My Email; local encrypted store; registers your computer as an Apple device. Needs an anisette server. |
| [dragosol/icloud-keychain-linux](https://github.com/dragosol/icloud-keychain-linux) | Read only | Terminal viewer and Firefox-family autofill, passphrase-encrypted on disk; the browser only ever sees the 6-digit code, never the TOTP secret. |
| [alex-mextner/passwords-app](https://github.com/alex-mextner/passwords-app) | **Two-way** | GNOME Keyring plus a GTK app, changes flow back to Apple devices. Created 2026-10-10: too new to trust. |
| [bendews/apw](https://github.com/bendews/apw) (257 stars) | Read only | CLI daemon for Apple Passwords. No Linux-specific guidance found. |
| [deej1721/icloud-passwords-linux](https://github.com/deej1721/icloud-passwords-linux) | Read only | Runs Apple's real Windows helper in a Windows VM and bridges it to Chrome. Heavy. |

**Risks common to all:** they sign in with your Apple ID and read or alter your keychain; anisette data comes from a helper or server you must trust; Apple can break any of them at any time; a mistake in a trust-changing step can affect other devices. Use a separate Apple ID to try one first if possible.

**Safer paths today:**
1. **One-way export.** On a Mac, export from the Passwords app to a file, import it into KeePassXC or Bitwarden on Linux, then delete the export (it is plain text while it exists). New passwords then live in the cross-platform manager, which syncs everywhere. No Apple sign-in on Linux.
2. **Read-only unofficial client** (`keychain`, `icp` or dragosol's) if you want to keep using iCloud as the source. Review its code, use an anisette helper you built yourself, and keep trust-changing steps off.
3. **Avoid two-way sync** until a tool has history.

**Owner lean (2026-10-14): a Brave browser extension.** Native Brave (1.97.56) is already installed on the M1 Pro. Two routes fit:
- **icp's extension (iCloud, read only).** Its README explicitly supports Brave: turn on Developer mode at `brave://extensions`, **Load unpacked** the project's `extension/` folder, copy the extension ID, then run `host/install.sh <EXTENSION_ID>` to connect it to the `icp` helper. It fills passwords, one-time codes and Hide My Email from a local encrypted copy of your iCloud Keychain. It needs an anisette helper and an Apple ID sign-in done by the owner.
- **Brave's own sync (no iCloud).** Brave Sync can keep passwords and bookmarks in step between Brave on the Mac, Linux and phone. It is a separate store from iCloud Keychain, so it avoids Apple sign-in on Linux but does not read Safari's saved passwords. It could be paired with the one-way export above to seed it.
- Also Chromium-capable: `keychain` (passkeys only) and `passwords-app` (Chrome autofill, two-way, too new).
Nothing was installed or signed in. Decide between icp-in-Brave and Brave Sync (or both) after the reinstall.

**Owner decision needed:** which path, and whether to try a read-only client at all. As with iMessage, an AI assistant must not enter Apple credentials; the owner signs in. Nothing is installed.

## Porting boundary

The current Apple Silicon behavior reference is
[omacom/omarchy-mac-pkgs](https://github.com/omacom/omarchy-mac-pkgs), audited
at main commit 222f7a8599bbdd287ac6a95362cd51c5b024baae. Its packages target
Arch Linux. This project should translate relevant behavior into Ubuntu,
mkosi, systemd, and Pantheon/Gala; it must not import Arch package scripts or
hooks. Apple-specific changes to those packages remain in that repository,
general Omarchy changes go upstream, and one-shot installation belongs in the
Omarchy Mac installer.
