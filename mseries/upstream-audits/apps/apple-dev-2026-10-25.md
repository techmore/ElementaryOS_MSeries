## Implementation and recovery

`rust/mseries-apple-dev/src/toolkit.rs` reads one literal `XTOOL_SDK_VERSION`
assignment as data and follows the SwiftPM SDK location used upstream:
`$XDG_CONFIG_HOME/swiftpm/swift-sdks/darwin.artifactbundle`, otherwise
`~/.swiftpm/swift-sdks/darwin.artifactbundle`. The installed stamp must match.
Warnings containing the word `darwin`, differently named SDKs and failed
`swift sdk list` commands cannot make the row Ready. A binary on PATH without a
successful xtool version response cannot make xtool Ready either. Neither check
executes the installer, builds software, opens the phone or changes credentials.

For an existing installation: Update the toolkit in Apple Dev, then use Install
with the selected mode. Updating the source alone does not rebuild installed
xtool, its private Swift runtime or an old SDK. For a stale full-mode SDK,
provide the matching Xcode `.xip`; Repair only reuses current cached bundles.
The toolkit's first-party functions own installation and rollback behavior.
No automatic repair or download is triggered by a status refresh.

## Validation and remaining evidence

The production non-GTK modules run in an isolated local harness because this
host is macOS: 43 tests and strict clippy pass, including real probe-script
fixtures for warning-only SDKs and failed commands. This harness does not build
the GTK window. Upstream's 11 Info.plist xcconfig tests pass; 15 framework tests
pass and one whitespace-only Bash-array case errors under macOS Bash 3. The
pinned upstream SDK-state and framework suites therefore run on Linux in CI.

The ARM64 app workflow builds/tests/packages the full GTK application and renders
current/stale SDK rows using `snapshot-sdk.sh`: private home/config, inert Swift
and xtool, light/dark, 780/1180 requested widths. The helper takes the packaged
binary so it does not trigger a second release build. Inspect the resulting PNGs
before claiming visual validation. No live owner desktop was restarted or installed.

The upstream October 25 fresh-install receipt is x86_64 Arch and stops at SDK
download; it is not a completed M1 Pro toolchain refresh. Actual SDK rebuild,
phone install, signing, TestFlight upload and owner UI acceptance remain separate.
The historical successful Rupert build in our October 23 handoff remains valid
within its recorded versions; it does not test this new upstream revision.
