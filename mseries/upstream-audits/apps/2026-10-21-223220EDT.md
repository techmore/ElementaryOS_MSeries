## Deep evaluation: Pika Backup on Ubuntu ARM64 + Pantheon

### Translation

Use the upstream GNOME project only through its existing Flathub app ID, `org.gnome.World.PikaBackup`, as an explicit user-installed Flatpak. Do not copy Omarchy's Arch/Snapper or package-manager behavior. Pika creates Borg repositories for personal files; its own product documentation says it is not a full-system recovery tool. It can target local/removable storage or remote Borg/SSH/SFTP repositories, encrypt archives, schedule backups, deduplicate known data and browse/restore individual files.

Flathub currently packages version 0.8.4 from GNOME runtime 50. elementary documents third-party Flatpak sideloading and AppCenter integration, but its AppCenter publishing requirements call for the elementary runtime. Therefore the precise low-effort translation is the upstream Flathub Flatpak installed by the user, not a claimed native AppCenter listing, apt package, factory payload, or Granite port. Keep it out of `packages.arm64` and the factory ISO. The app's GTK4/libadwaita presentation is acceptable as a cross-platform opt-in candidate, subject to visual review in the target theme.

The app is not narrowly sandboxed: the current Flathub recipe grants host filesystem access for selecting arbitrary backup sources and restoring them, along with network, SSH agent, and device access. This broad trust boundary must be explained before installation. Do not silently add an installer that hides the permission scope.

### Acceptance plan

1. Confirm that the target OS/AppCenter offers the current Flathub listing and aarch64 build, then install only for the requesting user. Record the exact installed commit/runtime and retain the upstream and Flathub source links.
2. In a disposable account or synthetic directory, create a local encrypted repository on removable storage. Test first backup, incremental backup, cancellation, archive listing, single-file restore, directory restore, incorrect/missing passphrase handling, and safe removal/reconnection of the destination. Never use real user files for initial acceptance.
3. Verify on Pantheon that the background portal permits scheduled runs after the main window closes, reports failure clearly, and handles an unavailable removable drive without losing the configured job. GNOME's guide describes portal-backed background monitoring and only lists Debian/Fedora as verified distributions; Pantheon behavior is open.
4. On the M1 Pro, measure one representative backup and restore for CPU/memory/disk impact and battery draw; verify Wayland file chooser and mount dialogs, permissions/ownership behavior, and restore readability with Borg tooling. Report these separately from architecture/build availability.
5. Confirm that no system paths are mistaken for a complete OS backup, that recovery instructions cover a clean OS reinstall, and that user data and the backup passphrase remain recoverable independently of Pika.

### Rollback

Disable scheduled backups in Pika and wait for any active Borg process to finish. Uninstall the Flatpak for the user. Keep the encrypted repository, passphrase, and any needed restore instructions; removing the app must not remove the only backup. Remove Pika's app data only as a separate, explicit cleanup after verifying the repository is readable. No service, kernel, boot, audio, display, panel, or factory-image changes are part of this proposal.

## Decision

No packaging/port spike is justified in this pass: Flathub already supplies an ARM64 build, and a repo-owned wrapper would duplicate elementary's optional Flatpak path while concealing rather than improving the GNOME app's sandbox and portal compatibility. The single best next iteration is an owner-selected, disposable-data Pantheon trial of Pika Backup; if the owner has a Sunshine host and wants that workflow, evaluate Moonlight as a separate opt-in.
