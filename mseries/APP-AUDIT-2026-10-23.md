## 3. What the SDK still cannot do (gaps, by how many apps need them)

1. **Panel indicator / popover host.** Wingpanel indicators and Switchboard plugs are plugins loaded into other processes. An SDK
   app is its own process, so it cannot appear in today's panel. The SDK `panel` and `popover` surfaces need the Rust panel
   (the Wingpanel replacement in the shell plan) or the Pantheon shell protocol client. Blocks about 10 apps.
2. **Services missing for declared capabilities:** notifications, timers (`every N seconds`), GSettings, keyring, folder chooser,
   HTTP/WebSocket, streaming subprocess output. The capability names exist; the calls do not.
3. **Components missing:** Transcript/Markdown/code block, Chart (sunburst, sparkline, bar), Tabs/Stack, Table, Calendar grid,
   Log/Terminal view, Image/Avatar, Menu, Toolbar groups. Recorded in `sdk-bench/GAPS.md` when first needed.
4. **Rules cannot parse or compute beyond `add`:** no JSON/text parse into list records, no arithmetic expressions, no
   conditionals except `when`. Those cases use `"logic": "rust"`.
5. **Panel anchoring:** `panel` surfaces open as plain windows until the Pantheon shell protocol client binds
   `get_panel`/`set_anchor`/`set_size`/`set_hide_mode`.

### Switching providers without re-sending everything

The concern: a conversation does not move between providers for free. Each provider needs the whole context again, there is no
shared prompt cache, and tokens are spent twice. The existing workflow already avoids most of it, and the router should keep to
these rules:

1. **Switch at task boundaries, never mid-thread.** A provider is chosen when a task starts; a running thread finishes where it
   started ([WORKFLOW.md](../rust/claude-pantheon-rs/docs/WORKFLOW.md), "Provider rotation by capacity").
2. **The handoff document is the issue plus the repo, not the transcript.** A new thread starts from a short brief (goal,
   acceptance gates, branch, files in play, decisions made) and reads the repository. Git is the memory; the chat is disposable.
3. **The local model writes the brief and the summaries.** Qwen-class on SER8 is cheap enough to triage (is the issue specified well
   enough for `agent:ready`?), classify the lane, pick the provider from capacity and task type, draft the brief, and write the
   closing handoff comment. Big models never pay for orientation.
4. **Keep prompt caches warm.** Follow-ups to a thread go to the same provider; a cache hit is the cheapest token there is.
5. **If a thread must move** (limit hit, provider outage): the router sends the brief plus the diff and the last decisions, not the
   history, and marks the thread as continued so the owner can see the seam.
6. **Resolve issues is the right first workflow.** It has a natural brief (the issue), a natural gate (the repo's checks and the PR),
   and a natural record (the closing comment). It also makes the SDK's gates meaningful: an app is "done" when its gates pass.

Router placement: a service in the T3 client (or the T3 server's scheduler) behind one message, `RouteTask(issue)`, returning
`{provider, lane, brief}`. In the SDK it is a Rust `Logic` plus a `call` to a local-model service; the rules engine cannot express
it. Not built.

## 4. Port order

1. Done: greeter, dock (logic and rendering; anchoring pending).
2. `mseries-updates` (task runner, already Rust, backend change coming with Arch).
3. Settings family: work-mode, touchid-settings, display-space, ui-scale, as standalone windows first.
4. Python task runners: polybagger print manager, phone-setup (wizard).
5. Dashboards and indicators once the panel host exists: codexbar, repobar, share-eyes, quick-settings.
6. List/detail: calendar (needs the grid), Torrential, notes.
7. Large: Orchard and Disk Space (they need the missing components, so they drive the next vocabulary).

**Reordered by the owner (2026-10-23): `claude-pantheon-rs` is the first priority app.** It pulls the transcript/markdown components, the keyring, notification and WebSocket services, the dialog/popover surfaces and the panel indicator host to the front of the SDK queue, ahead of the settings family.

The templates double as the first benchmark: a Qwen ~4B run that creates the first four archetypes from the spec text, using only
`msdk describe/complete/explain/gate`, is the early signal that the language is usable.
