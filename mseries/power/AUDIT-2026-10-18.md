# Power audit, j314s on Aurora `.20` — 2026-10-18 (Claude Code)

Read-only audit of the running desktop. **Nothing was changed**: no service, governor, display, audio,
kernel or bootloader setting. Tools: `mseries/power/audit/` (stdlib Python / bash, no root).
Sensor: SMC hwmon `power1_input` ("Total System Power"), 1 Hz.

## Conditions (matter for every number)
- Kernel `7.1.12-2-20261017.20-sep-ARCH`, up 1 h 10 min at start; matched `boot.bin` installed 04:32.
- **On AC** (`macsmc-battery` "Not charging" at 80 %, charge limit), so `power_now` of the battery is 0; the
  SMC total-system rail is the only usable meter. Built-in panel brightness 307/500, 120 Hz, VRR on.
- **Second display active**: 65" 3840x2160 on `card2-DP-2` (see the dock finding in the handoff).
- **Not an idle machine.** The owner's desktop was in use: Claude desktop, ChatGPT app, Brave, Signal, plus
  these agent sessions. An idle number cannot be taken without interrupting that work, so none is claimed.

## Measured (honest ranges, not "the" number)
| Run | n | median | mean | p10-p90 | CPU busy |
|---|---|---|---|---|---|
| A, 60 s | 60 | 19.72 W | 20.73 W | min 16.05, max 28.66 | 26 % |
| B, 240 s (my probes ran concurrently) | 240 | 25.04 W | 29.33 W | 19.53-44.54 | 44.7 % |
| C, 240 s (probes idle) | 240 | 21.36 W | 21.99 W | 19.38-25.52 | 33.5 % |

Run B's fit (11.07 W + 0.41 W per 1 % total CPU) and run C's (r² 0.04) disagree, so **watts-versus-CPU is
not a usable model here**: a per-second linear fit is dominated by display/GPU/radio state. Run B is inflated by
my own `/proc` scanners. Treat 19-22 W as the observed band for this workload with two displays; the
extrapolated "floor" of run B (11 W) is not a measurement. Rails at one instant: AC input 18.7-19.1 W,
3.8 V rail 7.0-8.4 W, heatpipe 7.0-8.2 W (SMC `power4`; meaning not documented).

## Who burns CPU (60 s averages, one core = 100 %)
gala 28.4 % (compositor, two outputs, animated Claude UI), claude-desktop 57 % + 24 % + 5 % (the app these
sessions run in), Brave renderer 19.5 % (one tab, 11 min CPU in 59 min), ChatGPT 10 % + 8 %, wireplumber
3.9 %, speakersafetyd 1.1 %, voxtype 1.0 %, wingpanel ~1.5 %, codexbar-linux 0.07 %, tailscaled 0.12 %,
incusd 0.2 %, touchegg 0.13 %, energy-poller/dashboard, netusage ≤ 0.1 %.
Context switches (30 s): ~7.9 k/s total; top are the SPI HID IRQ thread (811/s, trackpad activity),
asahi_sched GPU workers (4 x 365-800/s), gala 714, speakersafetyd 577 (high for 1 % CPU), rcu 262.
Cumulative CPU since boot of every system service is under 40 s (incusd 11 s, touchegg 6 s, bluetooth 5 s).

## State checks
- cpufreq `schedutil` on all three clusters (0.6-2.06 / 3.04 / 3.04 GHz); cpuidle driver `apple_idle`, 2 states;
  PPD `balanced` (placeholder platform driver); `mem_sleep` s2idle only; NVMe APST latency 100000 us (default);
  no failed units. No devfreq node, and no powertop/turbostat/perf on the box.
- Timers are sparse (sysstat-collect every 10 min is the only frequent one).
- Wingpanel/CodexBar polling cost is negligible (codexbar-linux 0.07 %, panel ~1.5 % mostly drawing).

## Applied
None. No candidate cleared the bar of a measurable gain on this noisy, in-use machine.

## Proposed (each needs the owner's OK; none is measurable as a watt gain on this meter)
1. **Brave renderer pid 43261** holds ~20 % of a core; find and close or suspend that tab. By far the largest
   single userspace item. (Largest candidate; effect would need a quiet A/B.)
2. **speakersafetyd** wakes ~577 context switches/s; it is a speaker-safety daemon, so leave it. Upstream
   question only. wireplumber 3.9 % is also audio stack: not touched.
3. Low-value service trims (cups, cups-browsed, avahi, rpcbind, lxcfs/incus with one container,
   smartmontools, geoclue, zeitgeist): each is <0.2 % CPU, so expected gain is under measurement noise.
   Only worth doing as hygiene, one A/B-able pass with the machine idle.
4. A proper idle A/B needs the owner's cooperation: all apps closed, screens at fixed brightness, on battery
   (or SMC rail on AC), ≥ 10 min per arm, three alternating arms. `power/macos-baseline/linux_profile.py` already
   defines that protocol.
5. Dock power: with the WD22TB4 and a 4K panel active, display scanout and Thunderbolt are a real part of the
   19-22 W; compare docked vs undocked in the same A/B.

## Not verified
Idle power; battery discharge rate; sleep drain on `.20` (the SMC sleep-energy hook exists, no record yet for this
boot); GPU/ANE rails; whether tab/video decode settings matter (Asahi has no hardware video decode); anything on battery.
