# Warren upstream updates: M1 Pro applicability — 2026-10-30

Source: [announcement](https://joshuawarren.com/blog/what-i-open-sourced-today-egpus-connectx-tensorfold/). This is an assessment, not an installation or hardware qualification.

The running host reported `7.2.11-elementary-aurora72-wip5`; `origin/dev` at `2c91b38d` pins its source to `2f725546`. A PCI inventory showed the Thunderbolt dock but no external GPU or ConnectX card. The running config says `CONFIG_DRM_AMDGPU` is unset. There was no `CONFIG_MLX5_CORE` line in `/proc/config.gz`; this alone does not establish whether all prerequisite options are enabled.

* [TensorFold #1526](https://github.com/ashhart/TensorFold/pull/1526) provides an opt-in Vulkan runtime and one Q4 projection, not a model-serving backend. The 2B engine is [#1544](https://github.com/ashhart/TensorFold/pull/1544), and the announced fast batching is a separate follow-up. Our [scoreboard](ENGINE-SCOREBOARD.md) already records an older experimental 2B build, including long-output divergence. Do not replace the existing server or claim the M1 Max result on the M1 Pro. Re-evaluate a pinned public engine and batching revision with matched-model fidelity and desktop responsiveness gates.
* [omarchy-mlx #303](https://github.com/joshuaswarren/omarchy-mlx/pull/303), merged as `42b30a2`, optimizes 2–4 row batched decode. Its M2 Max batch-2 result regressed, and M1 Pro is unmeasured. The project installer pins v0.7.34 and source `5e40ecf953e8b907dcae1ce6caadce6ad62b0e0f`; the upstream author says this change ships in the next release. Build a separate pinned candidate and compare batch sizes, token fidelity, memory and responsiveness before changing the installed runtime.
* [Aurora #188](https://github.com/omacom/linux-aurora/pull/188) merged after the wip5 source pin. It includes AMD non-posted BAR handling, Apple PCI tunnel scanning and T600x/T602x device-tree range changes. Hardware evidence is primarily M2 Max; the rebased PR and shared changes must be reviewed against wip5 and J314S dock/recovery behavior. Device-tree changes require a matching boot chain; a modules-only update cannot supply them. Do not silently replace the shared boot payload or default kernel. No local eGPU is present for qualification.
* [ConnectX-5 setup](https://github.com/joshuaswarren/omarchy-egpu/blob/main/cards/connectx-5/README.md) requires suitable hardware and `mlx5_core`; the author reports no special PCI or device-tree patch for the tested M2 Max. The RTX recipe likewise needs an external NVIDIA GPU. Neither hardware was visible in this inventory.

Next: pin and review a new Aurora source candidate including #188, compare its DTBs with the installed recovery path, build without boot hooks, and qualify dock, recovery and any actual eGPU on attended hardware before promotion. In parallel, qualify a released or exact-source MLX candidate against the current installed version. Preserve the existing worker and boot defaults until those gates pass.

Follow-up: a distinct [Aurora eGPU profile](../aurora/unified72/README.md#separate-egpu-candidate--october-30-2026) now pins the #188 merge and enables AMDGPU as a module; its native build was submitted to [CI run 41048473839](https://github.com/techmore/ElementaryOS_MSeries/actions/runs/41048473839). An isolated MLX #303 candidate passed the Qwen single-stream gate and three short batch pairs; the batch-3 result was mixed; both batch-4 routes are traced.
