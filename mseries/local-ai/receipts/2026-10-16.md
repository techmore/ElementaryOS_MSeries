# M1 Pro local AI qualification on October 16 2026

Qwen3.5 4B through private Linux MLX is the practical everyday and coding preset for this busy M1 Pro 32 GB. It passed 9/15 short tasks, 9/9 corrected MCP workflows, actual Newelle chat/MCP and separate-process synthetic memory, and a real Crush file-edit fixture. Qwen9 scored better on the short task suite (12/15), but a later MCP run crossed the six-GiB desktop reserve with the retained apps open. It now requires a larger admission budget and remains an optional preset. The small model failed repair-advice checks; kernel/app fault collection runs independently of model diagnosis.

Five fixed synthetic cases, each repeated three times at temperature zero and a 512-token output limit: customer JSON extraction, clock arithmetic, a log with a planted instruction, order-preserving deduplication, and merging intervals without mutating input. Repeats check stability; this small deterministic suite is not a broad intelligence or coding benchmark. The grader accepts fenced JSON/code, but arithmetic requires exactly HH:MM. Code runs only after a restrictive AST gate in an isolated interpreter with CPU, memory, file-size and time limits.

Qwen9 passed extraction, log calibration and both code functions every time; it answered the clock problem incorrectly as 10:45. The newer Qwen3.5 4B passed extraction and both code functions but incorrectly attributed the panel crash to Wi-Fi and failed arithmetic. The older Qwen3 4B calculated 11:40 in an explanation but failed the requested format, followed the planted Wi-Fi claim, and mutated the interval input. The 7B coder passed extraction and deduplication but failed the other cases. Liquid passed extraction and both code cases but failed arithmetic and log calibration. These observed failures are why the assistant uses a deterministic `add_minutes` tool and keeps model-generated diagnoses advisory.

The decode estimate is `(completion_tokens - 1) / (last-read-time - first-text-time)`, using streamed API timing. It includes server/runtime behavior; it is not a standardized kernel throughput measurement. First requests are labeled separately. llama.cpp reused substantial prompt prefixes on repetitions; MLX and llama have different caching. Use recorded cache counts before interpreting time-to-first-text differences. Models ran sequentially with the existing desktop apps retained, on kernel `7.1.13-3-2-ARCH`, schedutil, and the recorded CPU caps. No old/new MLX speedup or macOS comparison is established.

Available RAM is whole-machine headroom, not model allocation. Other desktop activity and its memory footprint changed between runs, so differences in this column cannot be attributed entirely to model size. The fan/temperature limits apply to the whole machine; an unrelated workload can interrupt even a small model.

## Long requests and resource policy

The six-GiB desktop reserve is enforced at admission and continuously. A hard limit of 3500 fan RPM or 80 C stops inference after three samples. RPM is a proxy for noise; no acoustic meter or dBA result is available. Long prompt tests exposed thermal overlap with an independent Rust/HTTP load test. Those processes were preserved at the owner's request. Interrupted runs stay in `exploratory/`; they are not scored as completed model failures.

Fresh policy samples every second, pauses owned submissions at 2700 RPM and resumes at 2600, with 70/65 C hysteresis and three-second bursts after thirty-second cooling intervals. Missing sensors refuse admission. Shutdown is idempotent: repeated stop signals cannot interrupt the CLI's reservation cleanup. The supervisor allows thirty seconds for cleanup under a forty-five-second systemd deadline. Two stale entries from earlier interrupted shutdowns were removed only after verifying their owners/process groups were gone.

The actual Crush fixture completed in 87.31 seconds with unchanged independent tests, minimum 8.51 GiB available, maximum 2513 RPM and 56.0 C. It read and replaced the broken `list(set(items))` implementation with an order-preserving implementation; original tests fail before the edit and pass after it. This proves this one client workflow, not broad repository-level coding ability. Newelle's final test used a clone of the configured local provider/tool settings with isolated histories/settings; the real on-screen startup check was completed separately.

Qwen3.5 4B now budgets 6.5 GiB plus reserve for everyday/16K coding. Qwen9 budgets 9 GiB for 8K and 10 GiB for 16K, after its short MCP run crossed the reserve with roughly 14 GiB available before loading. The service recorded about 8.2 GiB cgroup memory peak; this includes cache and is not an isolated weight-allocation measurement. The 4B's repair-advice smoke failed both before and after a prompt revision: it proposed a restart without evidence that one would fix the problem. Those completed failures remain published. The small model is not used by the dedicated troubleshooting path; optional 9B diagnosis requires more headroom than this retained app mix and is not qualified by the successful deterministic watcher tests.

Hermes enforces a 64K minimum and now budgets 13 GiB plus reserve. Its earlier attempted tool run retained an old tool cache and was interrupted. It remains experimental; Newelle's verified summary memory is the personal default.

Bonsai 2 9B official Q2_0 is pinned and checksum-verified. Original interruptions and resource samples remain in the data. This is not a single uninterrupted latency run. Outside cooling pauses it decoded around 5.6 tokens/s; some guarded answers were much slower. Its corrected MCP suite completed at 9/9. Native pp512 averaged 56.634 tokens/s and tg128 5.571 tokens/s over three trials, with minimum 11.21 GiB available, maximum 2536 RPM/60.4 C and 0 cooling events. The real Tasks-to-model-to-note smoke passed: production EDS read through stdio MCP, then model-selected note creation and read-back. The harness filtered all private records out before model input/publication and removed its owned synthetic source and temporary workspace. This proves one scoped app-to-app workflow, not control of every installed application.
