A teacher-forced follow-up reused the project's cached **CPU float32**, not FP64, Qwen 2B reference for the short rainbow prompt. Its 27 prompt IDs were regenerated from the same local tokenizer and matched the reference's prompt hash; the 32 reference generated IDs and their hashes formed the oracle. Reference logits were rounded to BF16 for the probe's diagnostic file, while the numerical calculation below uses the original float32 rows. The existing upstream `tf-qwen35-model --vendor 0x10005 --context 256 --teacher-forced` ran twice under the worker lock with a 4.5 GiB allowance, 6 GiB reserve and 80°C limit.

Both TensorFold runs matched all 32 oracle argmax IDs and were byte-identical to each other. All values were finite; versus the original float32 CPU reference the BF16 logits had RMSE 0.02884, compared with the installed MLX baseline's 0.03183 on these same rows (ratio 0.906, within the project's 1.15 per-case bound). This is one short case, not the full multi-case gate, the upstream FP64 fidelity gate, or an explanation of the later long-response divergence. The probe reports 6,437,111 unequal BF16 elements against the rounded CPU reference, so matching token IDs do not imply identical logits. [Probe result](teacher-result.json), [analysis](teacher-analysis.json), [log](teacher.log); the 16 MB logit matrices and oracle remain in the private cache.

The same teacher-forced procedure was then applied to the remaining five cached CPU float32 cases (32 rows each), holding the same worker lock and resource guards. Across all six cases, TensorFold logits were finite and repeated byte-for-byte. Pooled RMSE was 0.03526 versus the installed MLX baseline's 0.03647 (ratio 0.967, below the project's 1.05 pooled bound); the worst per-case ratio was 1.049, below its 1.15 case bound. There were no argmax flips where the CPU reference's top-two margin was at least 0.5. These are the project's numerical and margin checks, not a complete pass of its gate: free-running checks were not performed for all six, and the reference is float32 rather than the upstream FP64 gate.

The upstream probe's stricter exact-ID criterion **failed** in `single` and `code` (exit 1, same failures in both repeated runs). Against the CPU's teacher-forced argmax rows, the only differences were row 24 in `single` (reference margin 0.0041) and row 16 in `code` (margin 0.10039), both under the project's 0.5 near-tie threshold. The other four cases met exact-ID equality. Do not relabel the probe failures as passes: the project margin rule and the probe's exact-ID rule answer different questions. [Five additional case results and logs](multicase-results.json).

Across the 256 rows, TensorFold and full-pass MLX each differed from the CPU argmax only at this same near tie; TensorFold RMSE versus CPU was 0.02758 and MLX's was 0.02963 (ratio 0.931). This supports a near-tie explanation for the observed divergence, but does not establish the precise source of numerical variation or general fidelity.
