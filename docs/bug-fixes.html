M-Series bug-fix audit

Updated 2026-10-14. The installed elementary OS 9 desktop boots on an M1 Pro. The factory arm64 ISO built successfully on October 13; hardware boot remains pending. The evidence and reproducible next steps are tracked in the repository roadmap.

Resolved in the current source update

FindingFix
CodexBar quota exhaustion estimates were hidden in tooltips.The menu bar shows the earliest available quota ETA and its limiting window. Each dropdown limit shows a visible pace forecast or reset countdown; stale and unavailable estimates stay unknown.
CodexBar usage could lag by five-minute fetching plus one-minute panel reads.The native indicator reads snapshots asynchronously every five seconds and requests a throttled refresh when opened. One-minute backend polling is documented and applied on the working desktop.
Public status contradicted the recorded M1 Pro desktop boot.Pages now distinguish the installed transformed system from the unverified factory ISO.
CI path filters could skip changes to the transform script, root mkosi config, repositories, or arm64 package manifest.Added these paths to the M-series validation workflow.
The fork's scheduled builds needed elementary's private publishing credentials.Added a manual experimental arm64 build with retained logs, checksums, and installer artifacts. The first arm64 image build succeeded on October 13.
The hardware overlay pruned packages that its final image consumers did not explicitly install.Added runtime dependencies to both arm64 consumers and a regression test.
Overlay cleanup deleted the brightness helper and its desktop autostart entry.Retained the files and added a regression test using a temporary image tree.
ARM installer APT disc metadata used the amd64 directory; the ISO label also triggered a standards warning.Corrected target architecture selection and normalized the volume label. Rebuilt-image verification is pending.
The base image missed systemd-coredump, now included by current elementary OS 9 upstream.Ported upstream commit 7024fd04646a6a8565bf6805989b59fd72de928c.
Porting notes pointed at the retired omarchy-mac quattro branch for current package behavior.Recorded omacom/omarchy-mac-pkgs as the maintained reference and pinned the audited revision.
An older optimization audit listed ambient keyboard lighting as missing, though it was implemented and measured on the M1 Pro.Corrected the audit and listed the remaining lock, lid, and suspend checks.
Package notes said the Asahi speaker packages had no Ubuntu source, but resolute/universe provides the installed versions.Updated the package manifest and build notes. Factory-image audio packaging remains open.
Battery charge limit had no desktop control.Added a quick-settings switch and an 80% limit service; the limit reads 80% on the M1 Pro.
The Mac stayed awake with the display off when the lid closed on a USB4 dock.Added docked lid mode, which locks instead of retrying suspend. Running; a lid-close test with the dock is pending.
Network speed and usage were not visible, and the indicator was not part of the image.Added the speed graph and usage view, and pinned the build into the Apple Silicon image overlay.
No plain-language way to see what failed on the machine.Added the Local Troubleshooter, briefing and read-only assistant, all running on-device.
Dock Ethernet, hub and mouse were listed as unverified.Verified on a Dell WD22TB4 on 2026-10-14.

Verified on hardware 2026-10-14

CheckResult
Dell WD22TB4 Thunderbolt 4 dock on the M1 Pro (kernel 7.1.13 Fairydust USB4)The USB4 link trains, the dock enumerates, and the downstream USB hub, mouse and wired Ethernet work. Ethernet takes a DHCP lease and connects. The displays do not (see below).
Lid close, suspend (s2idle), lid open, resume without a dockWorks: a 14 minute 44 second suspend returned the moment the lid opened. The display controller powered back on and the login greeter started. Wi-Fi reconnected within about three seconds.
Docked lid mode (mseries-docked-lid)Running; it logged dock attached: holding the lid-switch inhibitor when the dock was plugged in. A lid-close test with the dock attached has not been repeated since.
